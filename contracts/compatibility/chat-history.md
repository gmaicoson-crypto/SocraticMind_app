# 移动端会话与分页历史契约

更新：2026-10-23，对应 M2-02 的读取子任务。新增两个只读端点，旧端点、旧响应 schema、消息写入和历史 Alembic revision 保持兼容。提供方是本仓库 backend；Android / Swift 消费者使用 [共享样例](../fixtures/chat-history.json)。

## 请求与响应

两个端点均要求 Bearer 鉴权，按当前用户过滤；`limit` 默认 30，范围 1—100。返回 `items`、非负 `snapshot_id` 和可空 `next_before_id`。

| 端点 | 参数 | 项目顺序与内容 |
| --- | --- | --- |
| GET /api/chat/sessions | mode=normal / socratic；limit；可选 snapshot_id / before_id | 每个有可见消息的会话一条摘要，按 last_message_id 倒序；包含当前标题、模式、主题、最后节点、角色、时间与最多 160 个字符的正文预览 |
| GET /api/chat/session-messages | session_id；limit；可选 snapshot_id / before_id | 该用户该会话的可见消息按 id 倒序；正文、metadata、附件与旧 HistoryResponse 一致 |

会话 ID 是不超过 100 个 Unicode 码点的非空字符串，查询参数须由 URL 工具编码，不手拼 URL。会话读取不局限于普通模式，节点 / 引导消息也使用原 message_type 与 metadata 返回，供后续学习组件使用。未知账号会话与不存在会话均返回空页，不泄露其他账号的存在性。

首请求不传游标，服务端取当前范围内最大可见消息 ID 为上界。加载更早页时，同时传回原 `snapshot_id` 和上一页 `next_before_id`，查询严格小于 before_id、且不超过上界。服务端多取一条判断是否还有内容；没有下一页时返回 null，不靠 items 数量猜测结束。刷新从无游标请求开始。

此“快照”只是固定 ID 上界，不是跨 HTTP 请求的数据库事务快照。新增消息不会挤动旧页；原有消息内容、生成状态、标题、删除和重生成可见性仍可能变化。客户端合并时按消息 ID / 会话 ID 去重；加载旧页不能覆盖已有的更新会话摘要，刷新时以服务端当前结果校正。分页请求不可跨账号、模式或会话复用；这些状态由下一阶段的功能状态所有者维护。

首个空页的 snapshot_id=0、next_before_id=null。删除后的空尾页可保留原 snapshot_id。输入不合法返回 422；401 保持认证失败，不转为空历史。双端拒绝倒序约定不符、重复 ID、超出上界、游标不前进、返回会话 / 模式不匹配等响应。可选业务字段用显式 null 表示；未知新增字段可忽略，metadata / attachments 的未知数据保留。

## 兼容与性能边界

旧 `/api/chat/messages?limit=&offset=` 和 `/api/chat/history/{node_key}` 仍保持原顺序与返回形状；后者仍是最早 50 条。移动端使用新端点解决完整会话历史问题，不把原节点端点假装成分页。空草稿会话由客户端按账号保存，未发送的草稿不出现在服务端列表。标题查询 / 请求 / 重命名、删除消息 / 会话、头像和建议继续复用原端点，未在本次改写。

客户端升级应先具备包含新路由的 backend；旧 backend 返回 404 时，上层应提示服务版本不支持并提供重试 / 配置入口，不静默全量下载旧消息模拟分页。同仓代码变更不代表部署同时生效。

列表只查询预览和标题，避免传输或在 Python 中加载所有正文 / metadata；历史只补齐当页附件与来源。复用现有索引和可见性过滤，无新增数据库迁移。列表聚合仍需扫描该账号该模式的相关记录，固定页大小不意味着数据库工作量恒定；大规模数据的 EXPLAIN / 索引调整与设备滚动性能仍待后续测量。HTTP 层继续保留响应字节上限，超大单页的 UI 恢复策略需在长消息阶段验证。

可见性 / 来源投影迁到 services/chat_history.py，由新旧路由共用；生成租约、取消、重生成和事务拥有者仍是原服务。SQLAlchemy 的列投影 / 加载控制用于减少不必要的数据读取，参见 [官方列加载文档](https://docs.sqlalchemy.org/en/20/orm/queryguide/columns.html)。

# 重新生成的完整上下文

更新：2026-10-25。本检查点补齐后端约束和共享样例；双端当前仍只开放普通文字 qa，下一步扩展请求与资格判断。此记录不代表完整重生成或 P03 已验收。

## 复用与边界

参考固定上游 `4a20228e630168113e9e09a66de83699545fa82c` 的 SocraticDialogue.retryAt：重用原问题正文、类型、引用及附件 ID，不从当前草稿重建问题。后端已有原问题绑定、附件快照、最新轮次检查和成功替换原回答的能力。本批沿用这些机制及同一事务，不创建第二套生成 / 恢复服务。

ChatRequest 已支持 kind、quote_text、quote_source_id 和 attachment_ids；未增加字段、路由或数据库迁移。新共享文件 `contracts/fixtures/chat-regeneration-contexts.json` 提供下列 6 种合成上下文：

| 情形 | 必须保留 |
| --- | --- |
| 有来源的引用 | 原正文空白、Unicode 引用片段和源消息 ID |
| 纯附件问题 | 空正文、附件 ID 顺序及原快照 |
| 引用与附件组合 | 同时保留引用来源和两份资料 |
| 旧式无来源引用 | 原正文与引用片段，不虚构源 ID |
| 主题概览 | 空正文、topic_overview、主题及原节点文本 |
| 节点概览 | 空正文、node_overview、主题及节点标识 |

样例中的历史记录是后续原生解码输入；提供方测试将实际历史的正文、目标、类型、引用、附件 ID / revision / accepted_coverage 逐字段对照，并核对回答绑定的原问题 ID。测试使用合成模型和临时 SQLite，附件正文来自合成解析块，没有真实用户文件或外部模型调用。

## 原问题校验与错误

`services/chat_regeneration.py` 从 lifecycle 提取原问题解析与重生成检查：优先用已持久化 ChatTurn 找原问题；旧数据无 ChatTurn 时保留按原回答前一条用户消息回退的行为。空缺 kind 仍按旧式 qa 解释。

- 原回答和请求必须属于同一账号、会话、模式、主题、节点及类型，原问题必须是用户 chat 消息，正文保持完全相同。
- 原问题的引用片段和源 ID 必须完全相同，不允许替换或省略。不同 Unicode 编码不会自动归一化。
- 继续复用附件资源归属、顺序和 revision / accepted_coverage 快照检查；本批不重写附件解析、绑定或清理。
- 只重生成最后一轮的终态回答；失败 / 中断保留旧回答，仅成功终态替换。新请求仍使用稳定 request_id，不增加自动重放。
- 原引用源不存在或不可访问时，HTTP 400 返回 `CHAT_QUOTE_INVALID` 与可读 message。之前该分支只返回 detail；原生实现需按明确错误码处理，并保留旧服务的通用错误回退。
- 原问题、类型、引用或附件已改变继续使用 `CHAT_REGENERATE_INVALID`；不是最后一轮继续使用 `CHAT_REGENERATE_NOT_LATEST`。确认拒绝后可用既有取消接口建立同请求的停止标记；不伪造生成成功，不重新发送问题。

事务、会话占用、取消标记与终态仍由 lifecycle 持有，提取的校验不提交事务。相比原实现没有增加数据库查询；新增检查读取已获得的消息字段。优点是普通聊天和后续节点聊天共用约束，避免静默丢失上下文；代价是旧记录缺失或原上下文不一致时必须拒绝，不能猜测一个可用问题继续生成。

文件规模：chat_lifecycle.py 从 864 行降到 806 行，历史登记上限随之下调；新模块 112 行。chat 路由保持 1216 行历史上限。它们仍是待继续拆分的历史大文件，没有新增或提高例外。

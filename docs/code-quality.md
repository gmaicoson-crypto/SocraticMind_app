# 代码格式与单文件规模规则

状态：M1 逐步实施，适用于 Android、iOS、backend 及手写工具脚本。Python Ruff 0.16.9 已接入；原生工具、统一脚本与 CI 状态见 [实施状态](execution-status.md)。数值是本项目的初始治理标准，不是语言或框架的强制标准。

## 每次修改后的校验流程

先检查可复用实现与[模块职责](core-modules.md)，再修改代码；完成后对变化文件运行格式检查和 lint，对文件规模与依赖边界做检查，最后执行修改及相关范围的测试。缺少工具或执行失败必须说明，不能写成检查通过。

格式工具统一排版，lint 检查常见错误，行数检查提示规模，测试验证行为；它们相互补充，不能相互替代。保存时格式化可选，CI 的只读检查是最终一致性依据。

| 文件 | 格式工具 | 相关检查 | 配置位置规划 |
| --- | --- | --- | --- |
| Kotlin / Kotlin DSL | ktlint | ktlint 规则、相关模块 Android Lint | 根 .editorconfig、android 工具版本配置 |
| Swift | SwiftFormat | SwiftLint 非重复规则、相关编译 / 单测 | ios/.swiftformat、ios/.swiftlint.yml |
| Python | Ruff Formatter | Ruff lint、相关 pytest | 根 pyproject.toml；后端与工具脚本共用 |
| Markdown / JSON / YAML / TOML 等手写配置 | EditorConfig 基础约定 | 编码、末尾换行、空白、语法与链接检查 | 根 .editorconfig、未来检查入口 |

SwiftFormat 负责排版，SwiftLint 中重复或冲突的格式规则关闭；不让两个工具反复修改同一写法。跨语言文件规模门禁由统一脚本负责，SwiftLint 的 file_length 规则不作为第二套独立门禁，避免计数口径不同。

工具能力依据：[Ruff format 只读检查](https://docs.astral.sh/ruff/formatter/)、[Ruff lint](https://docs.astral.sh/ruff/linter/)、[ktlint 配置](https://ktlint.github.io/ktlint/1.8.0/rules/configuration-ktlint/)、[SwiftFormat](https://github.com/nicklockwood/SwiftFormat)、[SwiftLint file_length](https://realm.github.io/SwiftLint/file_length.html)。实际参数和版本在 M1 固定并验证。

## 格式约定与修复范围

- UTF-8、LF、末尾一个换行、不保留行尾空格，禁止以压缩多条语句的方式减少行数。
- Kotlin / Kotlin DSL、Swift、Python 采用 4 空格缩进；Markdown、JSON、YAML 采用 2 空格。当前 .editorconfig 已配置通用 2 空格和 Python / Kotlin / Swift 4 空格；工具检查结果单独记录。
- Kotlin / Swift 每行宽度建议 120 字符，Python 延续源项目 100 字符。行宽和文件总行数是不同指标；不可拆分的 URL、字符串等按工具规则处理，不改写业务文本去迎合宽度。
- 引号、import 排序、尾逗号、换行由固定版本工具决定。Ruff 的格式与 lint 规则应兼容；不假设 formatter 会修复所有长行或 import 问题。
- CI 只做 check，不自动格式化、提交或推送。开发者本地 fix 后审阅 diff，再重新 check。
- 只对明确文件列表运行格式工具，但检查的是整个变化文件，不是仅检查新增的几行。格式修复可能改到同文件旧行，较大修复与行为修改分开审阅。
- 不对未修改文件执行全仓格式化。已发布的 Alembic 历史不为了排版改写；新 migration 提交前遵守规则。
- 默认不使用 lint 的不安全自动修复；修复类型注解、表达式等行为相关内容时应审查并运行相关测试。

## 统一入口规划

M1 计划在 scripts/quality 下提供基于 Python 标准库的调度器，调用固定版本语言工具，不自制 Kotlin / Swift / Python formatter。check_file_sizes.py 已实现显式文件规模检查，其余调度能力按后续任务接入；现有范围见 [工具链](toolchain.md)。

| 入口职责 | 默认输入范围 | 行为 |
| --- | --- | --- |
| format-check | 变化文件列表 | 按语言批量只读检查；未安装所需工具视为失败 |
| format-fix | 显式文件列表 | 只改选中文件，不自行扩大范围或暂存 |
| lint-changed | 变化文件 / 受影响模块 | 运行各语言既定规则 |
| structure-check | 变化文件与关联依赖图 | 计数、基线、例外、循环与禁止依赖检查 |

本地默认收集已暂存、未暂存和未被忽略的新增文件，去重并过滤已删除文件；部分暂存文件的 fix 会影响工作区，不能自动重新暂存。若提供 staged-only 模式，检查索引快照而非假定工作区与索引相同。

CI 使用已有的 PR merge-base / push 基线，处理初始提交、空格、中文、重命名、删除。空文件集合返回明确的“无适用文件”；存在业务变更却无法找到工具或映射必须失败。文件通过参数列表传递，不通过 shell 拼接路径。相同工具批量调用，避免每个文件启动一次进程。

版本、规则与 CI 缓存键一起锁定。规则配置改动时检查该规则涉及的文件 / 模块，不静默切成全量测试。基础全库清点仅用于建基线或明确的治理任务，不等于日常全量业务测试。

## 单文件总行数

对格式规范化后的手写源码计数。采用物理行数，包括空行、注释、import、文档字符串与多行字面量；没有末尾换行的最后一行也算一行。末尾换行不会额外算一个空行。这样双端与后端口径一致，不能靠删注释或挤成一行规避限制。

| 文件类别 | 预警值 | 硬上限 | 达到预警后的重点 |
| --- | ---: | ---: | --- |
| Android / iOS 页面、UI 组件；backend 路由文件 | 250 | 400 | 页面是否混入业务；路由是否承担编排 / SQL |
| 其他生产源码：ViewModel、service、repository、model、手写 DTO、工具脚本 | 300 | 500 | 状态、纯计算、IO、序列化是否混在一起 |
| 测试代码、测试 helper、测试工厂 | 500 | 800 | 按行为场景拆分，复用 fixture，避免整段复制 |

达到预警值（含等于）产生提示；超过硬上限（不含等于）阻断检查，除非存在有效基线或登记例外。低于预警值也必须保持职责清晰；小文件不天然意味着好设计。

分类以版本化路径 / 类型映射为准，优先级为：有效生成物排除 → 测试 → 页面 / 组件 / 路由 → 其他源码。不能通过改名或移动到 utils 目录逃避更严格分类；重命名需保留原记录并审查新职责。一个文件包含多种生产职责时采用更严格门槛，并提示拆分。

以下不使用普通源码行数限制，但不能作为塞入业务代码的容器：

- 可验证生成的 OpenAPI、生成 DTO、Gradle / Xcode 生成物、锁文件：按明确路径、生成器和来源记录排除；一个 generated 注释不足以豁免，手写包装代码仍受限。
- 数据型 JSON fixture、快照、提示词与文档：按场景拆分和独立的数据大小规则管理，不能将可执行逻辑藏入大字符串。
- 已迁入的历史 Alembic revision：保留原文并记录来源；新增 migration 默认使用普通生产源码 300 / 500 规则，需要更长的数据迁移时登记例外，不按行数机械拆断事务。

函数 / 方法超过约 50 行、单个类 / 状态对象超过约 250 行时，作为评审提示检查职责、嵌套与依赖，不在首期用不可靠的括号 / 正则统计做硬门禁。需要精确复杂度规则时采用相应语言工具并单独校准。

## 上游大文件与例外

源后端固定提交 `4a20228e630168113e9e09a66de83699545fa82c` 的物理行数抽查：routers/chat.py 为 1,275 行，services/chat_lifecycle.py 为 864 行，services/agent/orchestrator.py 为 856 行。它们已超过拟定限制，不能假装首次迁入即可全部达标。

1. 初次迁入分为来源核对、仅格式规范化和业务调整三个可单独审阅的步骤；保留原始来源摘要，最终基线用固定工具规范化后的行数。已发布 migration 保持原样。
2. 在 scripts/quality/file-size-baseline.json 下登记逐文件历史基线：本地路径、源 SHA / 原始摘要、格式工具配置摘要、规范化行数、职责分类、拆分方向。只收录可验证的迁入文件，不把新增业务代码混入基线。
3. 对仍超限的历史文件，日常变更后行数不得高于 PR 基线与登记上限二者的较小值；减少后同步下调登记值，达标后移除豁免。新增职责放到合适模块，不能往大文件继续堆功能。
4. 紧急修复、不可合理拆分的数据迁移等情况可登记精确例外：文件、规则、允许最大行数、原因、负责方、关联任务、复查日期与回收条件。默认复查周期不超过 60 天，不使用目录级永久通配豁免。
5. 例外和基线调整必须在同一变更中可审阅并被 CI 列出，不得以脚本自动抬高阈值；常规技术取舍在现有授权内完成，不额外引入反复确认流程。
6. 无效、过期或超过登记上限的例外阻断检查；文件删除后移除记录，纯重命名转移来源关系。失效条目检查可扫描登记表，不需要运行全量业务测试。

行数并非唯一门槛：即使通过基线，新增循环依赖、路由中直接编排 AI、UI 中处理 Token 等仍需整改。不能只移动代码到 ChatManager2、misc 或一个同样庞大的 helper。

## CI 与 M1 验收

quality/structure 在 Linux 上运行统一计数与边界检查，语言 formatter / lint 在对应环境执行。structure 的最终通过结果以格式检查通过为前提，避免格式化前后行数不同。质量汇总接收所有必要结果。

报告包含路径、类别、变化前后行数、预警 / 上限、基线 / 例外 ID、建议拆分方向。超过上限、无效例外、格式失败、禁止依赖或检查脚本异常均失败；预警保留到报告和 PR 说明。

M1 实现时对检查器做少量有意义的边界测试：恰好等于上限与多一行、UTF-8 / CRLF、末尾换行、注释 / 空行、删除 / 重命名、部分暂存、生成物伪装、例外到期和基线收紧。验证“不能生成 APK / IPA”的检查链路，只运行相关测试。

当前格式工具与显式文件行数检查已在本地运行；完整增量调度、依赖检查和 CI 尚未接入，不能把局部检查称为完整自动门禁。CI 范围见 [CI 规划](ci-and-collaboration.md)，实际拆分职责见 [核心模块规划](core-modules.md)。

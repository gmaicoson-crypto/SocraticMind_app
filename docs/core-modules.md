# 核心功能拆分与复用规划

状态：方案与实施并存。网络、账号与会话读取核心已开始落实，具体证据见[实施状态](execution-status.md)。遵循[架构方案](architecture.md)，先复用已有模块，再按变化原因拆职责；文件限制见[代码质量规则](code-quality.md)。

## 拆分依据

一个模块围绕一项稳定职责，有明确输入、输出、状态归属和副作用。优先拆容易单独测试的逻辑，以及需要独立取消、缓存、替换的 IO。先在目录 / 文件层拆分，再根据复用和编译隔离需求决定是否新增 Gradle module、Swift target 或 Python package。

收益是缩小修改与测试范围、减少界面重复和并发状态冲突；成本是增加接口与导航路径。只有一个调用点且职责简单时不新增转发层，不把每个函数拆成文件，不把大类切为共享大量私有状态的多份 extension 来规避行数。

编码前记录：已有实现在哪、复用还是扩展、状态由谁持有、影响哪些接口 / 消费者、需要哪些相关测试。发现第二个真实复用场景或明确平台差异时再提取公共组件；不要预建无人使用的万能模块。

## 原生客户端核心职责

Android 和 iOS 对齐功能语义，各自使用原生实现；下列名称表达职责，不要求强制生成同名文件。

| 领域 | 建议拆分 | 状态归属与复用 | 相关验证 |
| --- | --- | --- | --- |
| App / 导航 | 入口、路由、依赖组装、认证入口判断 | App 只连接功能，不承担功能状态机 | 路由恢复、未登录跳转、依赖注入 |
| Auth | 页面、会话状态、AuthRepository、CredentialStore | 凭证由会话 / 安全存储负责；页面不读 Token 文件 | 401、退出、账号隔离 |
| Chat | 页面、消息列表 / MessageItem、输入组件、ChatState、ChatRepository | 普通 / 节点模式复用同一组件；消息数据仅一处维护 | 模式、发送、重生成、消息动作 |
| 聊天流 | ChatStreamTransport、SSEDecoder、RequestRecovery | transport 管连接；decoder 纯解析；recovery 管请求状态协调 | 分片、终态、取消、重进程恢复 |
| Onboarding / Assessment | 分步 UI、流程状态、repository、结构化展示组件 | 服务端 run 为权威；客户端仅投影和提交事件 | 版本冲突、恢复、确认、重复点击 |
| Learning / Graph | 主题数据、GraphPresentation、布局 / 视口、渲染与节点详情 | 学习状态与画布变换分开；节点列表复用相同数据 | 状态一致性、布局纯函数、触控 |
| Plans / Progress | 列表展示、计划状态、统计投影、日期工具 | 时区集中处理；掌握 / 解锁算法留在后端 | 跨日、重排、统计边界 |
| Attachments | 选择器、上传任务、附件状态、预览与来源组件 | 上传任务以 ID 管理；输入区和历史共用附件展示 | 权限、取消、状态与引用 |
| Notes | 编辑状态、Markdown 预览、DraftStore、导出 / 画布 | 保存与绘制独立；文件导出不混入编辑器 | 防抖、切后台、迁移、导出 |
| Profile / Memories | 页面、表单状态、repository | 安全退出复用 Auth，文件选择复用 FileGateway | CRUD、注销与清理 |

ChatState / ViewModel 只协调界面事件、消息状态和服务调用，不塞入 SSE 字节解析、Markdown 解析、凭证管理、文件 IO。生命周期停止 UI 订阅与用户取消生成分开处理，业务取消由明确的协调入口调用服务端。

UI 拆分示例：ChatScreen 负责页面组合，MessageList 负责列表与滚动，MessageItem 负责稳定消息展示，Composer 负责输入和附件入口；仅把必要状态传给子组件。流式文本只更新活动消息，稳定 ID 和解析缓存避免拆组件后仍全列表重绘。

Repository 对外暴露业务操作与结果，内部复用网络和存储接口。新增 use case 仅用于跨 repository 操作或被多个界面复用的流程；不能把每个 API 方法机械包一层。

## 后端核心职责

迁入时保留上游布局，先核对行为与测试，再围绕实际修改增量拆分。routers、services、models 等目录本身不是职责拆分完成的证明。

| 核心领域 | 路由层 | 服务与数据职责 | 可复用边界 |
| --- | --- | --- | --- |
| 认证与用户 | 解析表单 / schema、注入当前用户、转换 HTTP 响应 | 凭证验证、用户操作、邮件验证码、头像文件处理分别明确职责 | 认证依赖、账户清理、文件存储能力 |
| Chat API | stream、cancel、history / message、session / title 按行为拆路由 | 服务编排负责完整用例，路由不重复 AI / 数据库流程 | 保持既有 URL、响应与 OpenAPI 标识兼容 |
| 生成编排 | 只接收 / 返回协议对象 | 请求启动、上下文准备、模型调用、流事件输出由窄接口协作 | 同一编排支持普通与节点模式 |
| 请求生命周期 | 调用开始 / 查询 / 取消操作 | request_id 幂等、租约、终态、恢复检查点统一拥有状态转换 | 唯一事务边界，避免各辅助模块自行 commit |
| 上下文与来源 | 路由不拼接长历史 | 历史裁剪、摘要、学习记忆、附件检索、联网证据各自提供输入 | 编排选择输入，领域服务保持可独立测试 |
| Agent | onboarding / run / assessment 路由保持薄层 | 状态推进、结构化 AI 调用、计划生成、评估分别协作 | 保留服务端状态机与版本冲突规则 |
| 学习计划与掌握 | 主题 / 节点 / 计划 / 进度接口 | 图谱校验、排期、掌握事件、解锁、统计各自明确输入输出 | 不把规则复制到 Chat 或客户端 |
| 附件 | 上传 / 状态 / 内容 / 引用入口 | 存储、解析、worker、检索、摘要、清理分别复用现有实现 | 上传事务与后台任务状态衔接明确 |

routers/chat.py 已先提取 HistoryResponse、可见性查询及来源 / 附件投影，新增历史读取子路由；原文件从 1275 减为 1216 行，历史上限同步下调。后续再按 stream / cancel / session 边界拆分，消除路由中的业务编排。服务已经存在的逻辑先直接复用，不再写一份同义服务。对外前缀 / 路径 / method / 状态码 / 鉴权和 operation ID 变化都要显式检查；当前读取改动详见[会话核心](chat-history-implementation.md)。

services/chat_lifecycle.py 与 services/agent/orchestrator.py 先梳理状态转换及事务拥有者；可以提取纯策略、上下文查询和事件构造，但不能因为拆文件把幂等检查、消息持久化和终态写入变成多次不一致提交。

后台任务只通过明确服务接口更新其负责的记录，所有取消、超时、重试与清理操作保留原有幂等约束。把长函数拆成多个函数本身不会改善性能；应减少重复查库、重复上下文读取与重复序列化，避免为“组件化”增加额外网络调用。

## 依赖与公共代码边界

- Android：当前按已存在职责建立 core:network、core:auth、core:chat，后两者复用 network，均为纯 JVM；app 组装平台存储与功能。独立 model / data / designsystem 是后续确有消费者时的拆分方向，不为填目录预建模块；领域核心不依赖 Android UI。
- iOS：Features 调用 MindCore 契约，Platform 实现从 App 注入；MindCore 不导入 SwiftUI / UIKit，也不通过全局单例读取页面状态。
- backend：路由调用 service，service 使用模型 / 查询 / 基础设施；基础设施不导入 routers。复杂领域间通过明确 service API 协作，不互相调用对方路由，也不让 core 持有具体学习流程。
- contracts 为三方数据契约与样例，不是业务实现库；不能在这里放 Python 服务、Kotlin 状态机或 Swift UI。
- 公共目录只容纳确有复用的稳定能力；chat 私有解析辅助留在 chat，不能把所有小文件塞入 utils / common。

M1 用版本化允许依赖清单配合构建系统 / 可解析 import 图检查已能确定的禁止边和循环；Python 动态导入、依赖注入与跨层语义仍需要评审，不能声称静态脚本能证明全部架构正确。无法解析的依赖在报告中列出，不能静默当作合规。

## 增量拆分步骤与验收

1. 记录待改文件现有职责、行数和引用方；从现有代码挑选可复用模块，列出计划移动的行为。
2. 先为风险行为选择或补充定向回归：SSE 终态、重复请求、取消竞态、数据库事务、Agent 恢复等。
3. 优先提取纯逻辑，再隔离 IO 和展示，最后调整编排；尽量保持公开接口，迁移调用方后移除旧副本。
4. 拆分与新增业务分别审阅，避免边搬代码边更改协议。涉及上游大文件时按基线逐步减少，不要求首次导入全部重构。
5. 运行格式、lint、文件规模、相关依赖检查及受影响测试；记录新旧职责、行数、测试结果和性能变化。

验收不仅看单文件是否达标，还要看是否仍只有一个状态 / 事务拥有者、是否保留 API / SSE 契约、是否无新增循环与重复实现、测试是否更容易独立运行。设备 UI 和性能只能在对应运行条件具备时验证，不自动构建 APK。

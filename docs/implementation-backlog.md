# 从规划到内测成品的实施任务

更新：2026-10-22。已按用户授权进入实施；逐项实际进度见 [实施状态](execution-status.md)。M0 的产品方向已确认，但任务还包含需要落实的资源和证据，不能据此把 M0 全部标为完成。

阶段定义见[交付总计划](delivery-plan.md)，P / J 编号见[产品范围](product-scope.md)。表中角色表示职责，并不表示已经有对应人员；一人可兼任。源仓库是复用起点，本仓库 backend 是后续服务端维护主源。

## 任务使用方法

每个编号建立一个可追踪任务，远端就绪后可转为 Issue。按表中依赖推进，每次只选择已具备输入的一项或它的独立子任务；按已授权范围实现并验证；远端就绪后再安排协作。

“关闭证据”必须对应实际提交和运行结果。实现状态与验收状态分开；某端没有验证条件时保留待验证，不能用另一端结果替代。一个工作包可拆为后端、Android、iOS 的小 PR，但共享同一个功能验收；PR 写明复用项、影响范围、性能取舍和未验证事项。

## 每个任务的完成规则

1. 先检查本仓库、源实现和官方平台能力，写明复用位置、职责与状态所有者。
2. 改动协议或服务端公开行为时，同步契约、双端消费者和兼容说明；不只更新快照。
3. 变化文件格式 / lint 和行数检查通过，依赖与历史基线满足现有规则；缺工具时如实保留未验证。
4. 运行变化及相关范围测试，记录选择依据、发现数量、结果和报告；所需用例为零不能通过。
5. 关联设备行为、性能、持久化与迁移验收，不用主机单测覆盖这些结论。
6. 对应 P / J 记录更新，剩余问题有明确归属；影响包和服务版本时更新交付记录。

分支使用 `<type>/gy/<topic>`，如 `feat/gy/auth-session`；提交使用英文类型和中文说明，如 `feat: 新增双端会话恢复`。没有 Git 提交 / 推送指令时，仅准备和验证改动，不把任务状态写成已经发布。

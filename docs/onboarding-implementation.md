## 复用与职责

以固定上游 `4a20228e630168113e9e09a66de83699545fa82c` 的 `frontend/src/api/agent.ts`、`OnboardingForm.vue`、`PlanPreview.vue` 和 learningAgent 类型为行为参考。复用本仓库诊断题、结构化 AI、图结构校验、排期、run 状态机、确认事务和学习记忆。Vue 不迁入原生工程。

本次补齐响应丢失后创建恢复、当前表单投影、过期预览保护和取消重放。持久化原语移到 `services/agent/run_store.py`，供学习编排与评估共用；`onboarding_creation.py` 只负责创建占位及参数摘要核对。确认主题 / 节点 / 计划 / 记忆仍在原事务中，模型调用不持有 run 行锁。创建方在 commit 前冻结版本快照，失败写入同样检查合法状态转换，避免提交后取消被迟到失败覆盖。旧参数校验失败时只将可选 input 投影置空，保留读取 / 取消入口。

好处是使用现有 AgentRun 主键与 JSON 状态即可处理并发，无需迁移或新增服务；代价是新客户端必须持久化 run 标识并核对版本，旧客户端省略新字段时仍保留旧行为。创建占位与处理状态一次提交，避免占位已可见但处理未开始时，被其他请求重复启动。详细边界见[协议](../contracts/compatibility/onboarding.md)。

## 原生接入顺序

1. 双端增加独立的学习领域协议和类型，复用现有鉴权传输、大小限制、错误投影及账号 revision。共享样例校验七种状态、UTF-8、日期、字段边界、缺失 / 未知字段和错误响应。
2. 单一状态拥有者管理目标表单、诊断、预览及确认。run ID 在发请求前保存，确认 ID 稳定；恢复只读服务端，再由用户选择继续、取消或重试。不把目标 / 回答正文或密钥写入恢复日志。
3. 表单提供主题、目标、领域、成果、熟悉度、每日分钟、目标日期、时区与可选诊断；预览显示节点、每日安排、延期及风险提示。服务端返回的 input 是恢复后的当前表单来源。
4. 账号退出立即清空内存，不将旧请求结果交给下一账号；尚未确认终态的本地 ID 记录按原账号保留，原账号重新登录后只读恢复。离线退出不能证明服务端已取消，直接删记录会失去恢复入口，因此不再按早期规划在退出时无条件删除 ID；它们不含凭证、目标或回答正文，终态确认后才清除。确认成功保留一个结果 receipt，供主题列表刷新并确认消费。
5. 接入双端宿主导航和页面，保持各自组件复用。新的宿主构建、后台 / 进程恢复、键盘和真实模型教学效果分别验证，不能以纯核心测试代替。

## 双端请求层进度（2026-10-28）

第 1 步的协议与传输先行接入：Android 增加纯 JVM `core:learning`，iOS 在 MindCore 中增加 Learning 目录。两端均复用现有 HTTPTransport 的鉴权、响应大小、超时和错误处理；表单、响应类型、解析及请求派发按职责分开。Swift 将回答用量已有的严格整数判断提取为 JSONScalar，供学习流程版本复用。后续状态与账号 revision 的接入见下文。

创建、读取、回答、修改、确认、取消、重试均有真实回环 HTTP 检查。修改显式传 null 清除日期；回答 / 修改 / 确认 / 重试携带版本；所有响应核对本次 run ID 和 onboarding 类型。协议层不自动重试写请求；确认 ID 由下述状态拥有者在首次创建前持久化。

共享样例包含七种提供方状态、十三组请求 / 错误、二十六组非法原始 JSON 及三组兼容响应。版本拒绝浮点 / 指数 / 布尔 / 字符串，日期验证真实日历，节点引用与 UTF-8 身份保持一致。额外字段不进入 UI 状态，终态不解析已失效的步骤 / 预览 / 结果；错误只保留已知 code，不展示模型异常正文。预览只保留列表和安排所需字段，后续图谱读取实际主题数据。

好处是新增流程直接复用现有传输与测试基础，可独立验证协议；代价是客户端解析预算需要随提供方协议演进维护，且请求层本身不能完成页面恢复。未接宿主依赖 / 导航，不新增模型目录或密钥配置。用户选择稍后配置模型，当前没有真实模型请求。

GET 404 与原 POST 在途可以同时成立，因此不能把“读取不存在”视为安全删除日志的证据。提供方补充取消占位后，双端已接入专用取消请求和核心恢复状态；实际进程终止与页面生命周期仍待宿主验证。服务进程中断后 processing 长期不变的限制同样保留。

## 未知创建取消提供方（2026-10-28）

新增新主题专用取消入口，复用 AgentRun 主键仲裁并在请求尚未到达时保留最小 cancelled 记录。后续创建遇到该记录直接返回终态；普通已创建流程继续保持参数摘要约束。取消事务从 orchestrator 移入 run_store，原导入入口保留，新增类型检查避免误取消评估或已有主题计划。无需迁移、不加载模型配置、不写入目标正文；并发插入失败先 rollback，再读取 / 锁定胜出的记录。

好处是客户端无需保存完整表单重放创建，也能安全放弃未知请求；代价是服务端必须保留取消占位，不能随客户端日志删除或随意过期。创建先发生时只保证阻止结果回写，不能保证上游停止计费。现有通用 cancel 保持“仅已有记录”的兼容行为。

HTTP 覆盖先取消后迟到 / 改参创建、重复取消、无模型配置、他人 / 其他流程、已完成保护、无效 UUID、未登录及无关完整性错误；真实 MySQL 独立连接覆盖旧快照、双方主键竞争、同时取消和模型迟到成功 / 失败。提供方验收证据不代替下述消费者检查或原生页面验收。

## 双端状态与恢复日志（2026-10-28）

两端 cancel 已切换为新主题专用路径，并通过实际回环 HTTP 解码无 input 的最小取消记录。OnboardingController / OnboardingModel 是单一事务拥有者：首次创建前保存账号 ID、run ID 和稳定确认 ID，保存失败不发请求；回答、修改、确认与重试使用当前已观察版本。失败或 409 后要求重新读取，不自动重发写请求。processing 只追加最多三次延迟读取，结束后由用户刷新或取消；取消可以替代本地正在等待的请求，但迟到响应不能修改当前状态。

恢复日志复用 AccountFileStorage 的有界原子 IO、写入核验和按账号 / 服务地址分目录规则。Android 将该实现从聊天模块移动到纯 JVM core:storage，聊天与学习共同依赖；iOS 移到 MindCore/Storage。现有聊天、头像命名空间和字节格式不变。学习日志使用独立 onboarding 命名空间、schema=1、最多 4096 字节；旧记录不匹配、损坏、非法数字 / ID 或超限时拒绝覆盖 / 清除。互斥锁 / actor 归日志实例所有，每个后端只创建一个实例。

只有确定 completed / cancelled 后才清理对应记录。完成结果保留为 receipt，消费前不能开始下一流程。清理或清理后的核验失败时保留已知终态和待清理 ID；刷新仅重试幂等清理，即使文件实际已删除也不丢失内存中的完成结果。进程在清理成功后终止时不承诺 receipt 跨进程投递，后续主题列表必须以服务端数据重新加载，不能依赖一次通知才能展示主题。

SessionStore.authenticated 负责凭证及 401 / revision，状态拥有者另外核对账号与操作序号。Swift 在 actor 边界异步读取会话，宿主须 await bindAccount；两端都拒绝过期账号绑定和旧请求回写。退出清空内存、保留原账号未终结 ID 的修订见第 4 步。好处是离线 / 超时不必落盘正文或重复创建，代价是错误时需要用户刷新或取消，以及少量待清理 ID 留存。

目前核心状态包含运行投影、忙碌 / 恢复标记、错误类别、待处理标识和完成通知；表单原始编辑值、问题输入组件、模型目录复用、宿主导航和页面仍待实现。纯 JVM / macOS 包测试不证明 Android / iOS 进程恢复、备份排除或原生交互已经通过。

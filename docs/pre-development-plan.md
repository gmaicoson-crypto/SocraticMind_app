## 后端纳入本仓库的原则

后续从源提交迁入 backend 代码、相关 pytest、Alembic 历史、必要资源、依赖与工具配置，并保存许可证与来源记录。来源核对、格式规范化和功能调整分开审阅；迁入大文件登记基线，后续按相关功能逐步拆分，初次迁入优先保持行为，再按需求迭代，不把移动端建设变成后端整体重写。

本仓库是移动项目后端的维护主源，不向原仓库自动回写；上游修复按需审查并定向验证。Android、iOS 和 backend 的相关修改可以同 PR，但发布分别进行，兼容仍在使用的旧 App 版本。

代码复用不会自动复制用户、账号或学习数据。后续若需要原产品的数据，另做迁移方案，不让两个可分化的后端无约束共用同一个数据库。backend 已迁入并记录来源，尚未复用原产品数据。

## 产品和实现边界

复用原后端的账号、主题、计划、评估、记忆、对话、附件和模型配置实现；移动端负责展示、输入、平台能力与恢复体验。保留源项目的苏格拉底学习方法，不在 App 里另建一套判断掌握、解锁图谱或规划时间的算法。

手机端按任务拆页：今日学习 → 主题 / 图谱 → 节点对话 → 评估 → 进度更新。普通对话与节点对话在各平台内共用消息、输入和来源组件；不同模式通过显式参数表达。主题创建必须先经过目标收集、可选诊断和计划确认。

M0—M5 的退出条件统一维护在[交付总计划](delivery-plan.md)，不另维护一份不同的完成标准。M0 的开发身份已确认，M1 正在推进，M2—M5 尚未完成；M5 必须包含实际安装、运行、恢复和维护交接。

不在未知团队人数、每周投入与真机条件时承诺具体日期。按里程碑验收推进，M1 验证后按三方实际投入及外部等待校准工作量。

M1 可先完成 backend 的定向 pytest / 隔离迁移验证，以及 Android JVM 与 Swift 包的相关主机测试；客户端单测会编译被测代码，但不生成 APK / IPA。设备 UI 验证另行安排：Android 仪器测试可能构建 APK，iOS 模拟器测试会编译应用宿主。没有对应运行条件时保留“未验证”，不能以单元测试代替原生验收。

## 首次实现应验证的关键风险

1. **后端基线**：验证迁入范围、许可证、工具配置、依赖与 Alembic 历史；用隔离数据库和 mock 确认相关功能，防止遗漏上游根目录依赖。
2. **SSE 和恢复**：Android / iOS 的 POST 流、Authorization、中文跨 chunk、后台挂起、回前台恢复、停止与重复点击。先确保原生传输与共用契约一致，再开展完整聊天界面。
3. **键盘和导航**：输入框不被遮挡，切换页面不泄漏订阅，系统返回与页面历史一致，字体放大可用。
4. **图谱与长对话性能**：固定图谱 / 消息样本验证，两端均可操作；验证原生 2D 图谱和消息列表；Three.js 只作行为参考，不承诺还原全部 3D 动效。

## 质量规划落地顺序

M1 先统一各语言格式工具版本与 EditorConfig，再实现增量文件列表、格式 / lint 入口和行数检查；核实上游文件后登记历史基线。随后建立核心依赖允许清单与相关测试映射，最后接入 CI 汇总。规则先在少量边界用例上验证，不通过自动放宽限制让检查变绿。

具体阈值、计数方式与例外见 [代码质量规划](code-quality.md)，客户端与后端拆分见 [核心模块规划](core-modules.md)。实现进度和实际检查结果见实施状态，不以规则文档存在当作门禁通过。
